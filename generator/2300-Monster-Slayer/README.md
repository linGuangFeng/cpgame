# Monster Slayer 2300 Java Loader — partial repair

Status: ordinary model verified; complete special-state generation remains blocked.

The dependency-free Java 17 Loader JAR uses SecureRandom. Ordinary boards are sampled independently per cell using `generation.symbol.N.normal-weight` counts from 1,237 original paid first pages (15 cells = 18,555). Scatter stays off reels 1 and 5 and is capped at one on ordinary boards. The model excludes the 100 reserved complete Rounds. It rejects boards violating original ordinary symbol/Scatter constraints or the requested outcome; it never changes sampled cells to force a win or loss.

Generation, codec validation and Redis writes are streamed in batches. generation.batch-size is the maximum number of complete rounds per batch, not a Redis command count. Each cycle generates at most one batch of losses, one batch of wins, then one batch for each purchase mode, skipping completed or zero-count modes. A large loss target cannot delay all winning and purchase rounds until it finishes. Each validated batch is committed in one transaction before generating the next; rounds and write commands from earlier batches are released. Retry limits and cumulative progress use long arithmetic. Each committed batch emits BATCH_COMMITTED with batch number, batch members and cumulative loaded count; LOAD_COMPLETE appears only after all requested rounds have been committed. The Loader reads the endpoint, authentication, database and Redis game ID from its configuration. The repository defaults are 192.168.10.3:6379 DB15 / game ID 2300; the admin uses dist/generator.properties, whose deployment settings are preserved when packaging.

A run replaces each requested pool once, after that pool’s first batch passes validation. Ordinary losses and wins share a single reset; zero-count pools are left untouched. Cleanup reads old index entries in bounded pages. Later batches append to the same pools, honoring generation.max-members-per-multiplier for ordinary rounds and generation.special-max-members-per-multiplier for purchases. A failure or interruption leaves already committed batches in place and stops further generation; there is no automatic resume. Progress counts committed rounds, while retained Redis list sizes are bounded by the per-multiplier caps. Key prefixes are mode 0/1/2 followed by the eight-digit padded redis.game-id (1..99999999). For example, game ID 8002300 uses 008002300, 108002300 and 208002300. Remapped IDs do not delete the unscoped legacy PerKeyListt_* indexes. Only four indexes are written: PerKeyList_0 for ordinary results and MaryKeyList_0/1/2 for the three purchase modes (each prefix includes the configured padded game ID). The previous PerKeyList_1/2 purchase aliases had no BetLog result lists and are no longer written; pool initialization removes old aliases. Existing default-ID callers remain compatible.

Configuration is read once at startup. Editing the file during a run affects the next run only; interrupt and restart to apply it. LOAD_START records the loaded counts and config path. Natural special generation is unsupported, so the distributed configurations do not expose generation.special-count, natural-feature weights or a trigger-weight option. Older files may omit generation.special-count or set it to 0; both disable that mode and load normally. Positive legacy values are rejected rather than silently treated as generated.

The default generator.properties requests 300 ordinary losses, 300 ordinary wins and 80 captured purchase Rounds per mode. Natural special-state generation is still unverified and unsupported; no configuration for requesting it is shipped. Purchase Rounds use the bundled complete-round capture corpus.

On Windows, double-click dist/start-generator.cmd; it locates its JAR/config using its own directory. --no-pause suppresses the final pause. The admin runRedis entry launches this JAR and config from dist; the repaired package was verified through that Windows admin entry. Java -jar with no config argument also locates generator.properties beside the JAR.

10,000 new ordinary complete Rounds and 1,331 original ordinary payouts passed an independent DP oracle. The holdout covers 94 verified ordinary Rounds and 6 blocked special Rounds; it is not a completed 100-full-Round all-mode validation.
