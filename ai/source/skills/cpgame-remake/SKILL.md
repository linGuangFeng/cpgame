# CPGame 游戏复刻流程

## 先读与范围

- 先读工作区 `AGENTS.md`、`AGENTS.md` 和根目录 `复刻要求.md`、`抓包要求.md`，按其中的「统一适用口径」处理冲突。
- 下文产物路径均相对 cpgame 根目录；业务正文与 admin/ 均在本仓根目录内。
- 游戏目录固定为 `{gameId}-{English-Name}`。已有该游戏规则与协议时先读，不把夜市字段、符号、模式或概率套到其他游戏。

## 执行步骤

1. **盘点已有成果**：检查 resources、captures、fixtures、publish、protocol、generator、server-api、reports。复用有效内容，只补缺口。
2. **收齐原站资源**：按《抓包要求》真实点击进入游戏并操作各交付语言下实际存在的入口。完整操作两遍，第二遍没有未保存的新资源；只下载浏览器已经观测到的 URL，记录状态、大小、哈希、语言和交互清单。
3. **解析协议与规则**：从当前游戏帮助、赔表、前端、配置及当前游戏真实协议请求/响应确认完整 Round 边界、命令字段、符号、中奖与特殊模式。逐阶段列出符号允许位置、首列禁出、每列数量上限、互斥 / 堆叠 / 锁定与补牌约束，标明证据与未知项，不能仅解析赔表。保存原始证据，产出协议三件套，保证 rulesHash、behaviorIds 与能力状态一致。
4. **采集真实完整局**：先按《抓包要求》第四节建立采集计划、玩法覆盖表；落实 10 局最低复核线、基础中奖 / 未中奖各 3 局及每种特殊模式 2 个完整局，同时核对规则证据与结算，不按数量自动判完成。200 / 100 / 30 为扩展参考，按缺口每批 10～20 局追加，最多 3000 个真实付费 Round；提交有样本索引的停止报告。中断局、History、fixtures、本地生成结果不能凑数。加密或稀有玩法导致不足时记录 SAMPLE_INSUFFICIENT 与替代证据，继续可独立完成的工作，但不能宣布采集完成或完整复刻；玩法覆盖和权重统计分别验收。
   同时按《抓包要求》3.4 从可解析原站样本分组统计牌出现次数，产出可追溯的默认权重；区分连续样本与按结果定额采集的偏差，样本不足不得猜值冒充统计。
5. **固化游戏规则**：按 `write-game-rules` 写 `ai/source/games/{ID-Name}/` 并同步，后续规则变更同步更新协议和游戏规则。
6. **定义紧凑编码**：按《复刻要求》的「缓存编码（硬门槛）」与 `cache-result-encoding`，记录符号表和完整局 / 步进格式，任一分隔符占比不得超过 20%。
7. **实现独立 Java 核心**：实现规则、编解码及 SiUtil 对等组包入口。选局、钱包、单号生成、Redis 和 HTTP 由外围负责；Demo 壳 / JS 不能重复实现玩法。核心能脱离 Lab 编译测试，对照独立证据复核，并验证同结果换余额 / 单号只改变相应字段。
8. **接入 Demo 壳和结果源**：离线生成 / 装载工具复用 Java 规则和编解码；落实《复刻要求》第九节的配置与循环：样本基础权重、每牌倍数默认 3、每批不放大后逐牌放大、不累乘、无效候选计入尝试次数且不补足，所有 Step 必须满足牌阵约束；Demo 从 CPGame 规则约定的 Redis 读取预生成完整局，注入核心。Redis 不可用或为空时修复 / 报告，不得回退内存池、fixtures 或现场随机。旧备份里的生成器次数、默认局数量等不能自动恢复为当前要求。
9. **发布与启动**：按 `cpgame-publish-layout` 整理原站前端包，按《复刻要求》第十节接入对应游戏的有效本地管理封面并真实检查列表展示、保留截图，仅在允许的 __demo 旁路接入本地服务。交付当前 Lab contract v3 的 controller.jar 和 properties，按第十六节核对最新包已到实际下载/启动目录；已运行进程不要求重启，用户要求启动时再按 `restart-cpgame-lab` 执行。
10. **真实验收与交付**：运行 `verify-fc-lab-playable`，打开 /CPGame、进入游戏、确认 Demo 主界面与官方参考1、实际转一轮并保存截图。结合核心验证和证据清单，按 `AGENTS.md` 的完整验收定义报告成果与缺口。

## 完成标准

完整复刻同时满足：独立 Java 核心验证、资源 / 协议证据可追溯、Demo 真实点击可玩。报告核心与壳路径、测试结果、截图及样本不足 / 未验证玩法。只完成一部分时明确范围，不能仅凭 API 成功声称完成。


### 生成次数与结果容量统一口径

按《复刻要求》第九节：总生成尝试次数仅 `generation.count`（默认 1 亿），每批 `generation.batch-size`（默认 1000）；一轮权重等于一批，末批按剩余次数，失败候选不补足。Java 分类有效完整局，逐批按模式 × 倍数写 Redis。各桶容量可配并可逐桶覆盖，追加后保留最新 N 个、淘汰最旧结果；此授权仅限当前结果桶，不能清库。尝试数、有效数和现存数分别报告。验证显式小批量，不能自动跑默认 1 亿次。


### Redis 家族 / 类型映射

按《复刻要求》第十一节：普通 PerKeyList/BetLog 与 Mary（免费选择 / 免费特色）MaryKeyList/MaryLog 两个家族，各有默认类型 0、扩展类型 1、2、3、4…；不是固定四种 key。无关免费特色的额外场景走普通扩展类型，不把“特殊”一律归 Mary。先核实游戏入口与完整局，再记录稳定映射及 key / 倍数单位。普通容量默认 300、Mary 默认 50，支持按类型及倍数桶覆盖。管理端须发现任意实际类型编号及相同编码命名空间，不能仅枚举 0..3。参考 CP2470 普通/转盘/特色分别 Per0/Per1/Mary0，CP2300 三种购买分别 Mary0/1/2，禁止照搬其玩法。


### 显式配置与中文注释

遵守《复刻要求》第十二节：不要求 Redis namespace 或版本号，不设 v0 等默认版本，不因缺少 redis.namespace 判为配置缺项；不得为满足规则强加版本前缀。沿用当前游戏实际 key 合同，生成器、Controller 与管理端保持一致。其余必需配置仍须显式填写，包括每牌 weights.boost.<符号>=3；注释、单位、示例和可选逐桶容量继承规则用中文。已有前缀是项目现状，不是通用必需项；修改现有 key 须单独验证，不能因此清库。


### 试玩与正式生成链路（硬约束）

遵守《复刻要求》第十三节：试玩配置必须指向 Controller 实际配置，与生成配置分开；Demo 只从 Redis 读正式生成器产生的完整局，使用同一 Java 核心，不得另写玩法、现场造局或由 AI 手工准备中奖结果供验收。生成按游戏规则和符号分布先生成事实再计奖，禁止按目标奖金反推牌面或用采集完整局当模板。交付正常生成运行记录及试玩实际取局 key / 哈希。试玩支持各场景及六档实际押注倍数概率（0、(0,5]、(5,20]、(20,50]、(50,100]、(100,10000]），抽目标后只向下找同场景最近有效桶，可跨档但不得换场景或造局。无数据明确报错。索引整数放大系数按游戏核实或用户指定；生成器倍率上下限配置直接填写最终写入 Redis 的整数缓存倍率，范围过滤、ZSET score 与列表 key 使用同一个整数，禁止配置后再次乘除；核心接口单位不得重复换算。


### 防样本模板假生成（验收硬约束）
遵守根目录《复刻要求》第十五节，覆盖每个普通/免费/转盘等场景：审查正式生成调用链，禁止抽采集局、拼接样本或固定样本中奖组合冒充规则生成；区分有证据的有限规则表与有限样本模板。逐场景建立规则允许/实现支持/配置启用/实际观测的可达范围表；用正式入口做显式小规模审计，按完整事实及结构统计入库前多样性、倍率分布和拒绝原因，分清生成次数、唯一局数、ZSET 倍率数及保留后 LLEN。只有随机调用、很多结果、迁移一致或页面可玩不能判合格；桶少也不能直接判假生成，更不能为凑桶造倍率。样本模板或无依据缩窄分支判 FAIL，证据不足标 PARTIAL / SAMPLE_INSUFFICIENT。报告写入 reports/{ID}/generation-audit.json 或等价文件，并链接协议/游戏规则；历史游戏不因新增规则自动通过。


### 变更后的交付包（完成硬门槛）
按《复刻要求》第十六节：相关代码、依赖、资源或随包配置变更后，必须重新构建并更新所有受影响的实际交付包及下载归档；核对页面下载/下次“运行”引用路径、构建与 dist/发布副本内容一致，不能只更新 target。共享核心改动同时检查依赖包。已启动的进程不用管，不为完成打包自动重启或中断任务；保证用户下载和下次新启动取得最新包即可。交付说明实际包路径及验证结果，失败不能宣称已更新。仅规则/文档改动不影响包时不要求重打包。

### 免费中再次触发默认关闭
按《复刻要求》第十七节：默认免费过程中不再次触发/追加免费，只有用户针对该游戏特别说明才开启。记录为用户本地策略 DISABLED_BY_DEFAULT_POLICY，与官方规则事实分开；不列为默认范围的待补功能，不自动开启，也不自动提升其他未验证项。正常进入免费、原有计奖/倍率不受影响。现有拒绝相关候选的方式可沿用，计尝试且不补足；原始审计保留，当前解释为策略过滤。单游戏例外写入协议和游戏规则。
