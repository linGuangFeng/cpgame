# Monster Slayer 2300 protocol specification

Rules version `2300-monster-slayer-v8-rule-generated-hunt`; rules hash `4de0fb37e9c562faf5061807574052b5da97f98a2540cd41691426c5a101b057`.

The original Cocos page calls `POST /cp/config/initialData`, `POST /cp/account/getUserInfo`, `POST /cp/single_game.Game/initRoom`, `POST /cp/single_game.Game/gameResult`, and the two captured History endpoints. Requests are form encoded. A paid start is `type=1`; purchase starts are `type=3/4/5` (`SPECIAL_BUY_ONE/TWO/THREE`, buy multiples 60/500/200); every evidenced continuation is `type=2`. The response envelope is `{code,data,msg,time}`. `f.gt` 4 (`FREESPIN_SUPER_REWARD`) is evidenced in buy-mode `100002300` round-007 step-014.

`res.ps` is a non-empty column-major 5×3 integer board. Symbols 1–10 pay. Symbol 100 is Scatter. During the monster feature, zeroes are feature placeholders whose visible monster/wild identity is carried by `f.loc`, `f.a`, `f.r` and `f.rbs`. A win connects identical symbols from reel one across adjacent reels; each next position must remain on the same row or move one row. Three, four and five-reel payouts are the values in `rules-core.json`; `res.wa[].wy` is the ways count and `res.wa[].ws` contains the contributing cells.

Two Scatters start an evidenced monster mode (`f.nt` 1 or 2). Saved complete chains cover `f.gt`/`f.nt` 1, 2 and 3 and terminate only at `f.nt=0`. `f.h`, `f.a`, `f.loc`, `f.r` and `f.rbs` are preserved on every feature response. `f.gt=4` (`FREESPIN_SUPER_REWARD`) is wire-evidenced in buy-mode `100002300` round-007 step-014 and is generated by the mode-3 stop counter transition at 20 stops.

Redis endpoint, DB and game namespace follow deployment configuration; the following key examples use game 2300. Ordinary miss/win: `PerKeyList_000002300` + `BetLog:000002300:%06d`. Purchase buckets stay on distinct prefixes and never share a LIST with ordinary members: `MaryKeyList_000002300` + `MaryLog:000002300:%06d` (type=3 ×60), `MaryKeyList_100002300` + `PerKeyList_100002300` + `MaryLog:100002300:%06d` (type=4 ×500), `MaryKeyList_200002300` + `PerKeyList_200002300` + `MaryLog:200002300:%06d` (type=5 ×200). Type=3 does not write `PerKeyList_000002300` because that index is ordinary. New ordinary members retain compact ASCII `MS3`. New feature members use binary `MS4B` (raw bytes in Redis), with delta-coded ASCII state plus length-prefixed `HTB1` hunt traces (uvarint integer facts, no CSV/Base64). HuntRules independently replays the decisions; Controller reconstructs `f.r` from those facts. Runtime purchase generation never loads captured round templates. New members use neither compression nor Base64; hunt facts are raw `HTB1` bytes inside `MS4B`, not text CSV. Legacy `MS1`/`MS2` and earlier `MS3` remain readable, but old feature buckets must be rebuilt after all consumers update because their stored multipliers omit feature effects. No zero-payout monster-chain delivery is elided. Ordinary and purchase centi-multipliers are both `roundTotalWin / baseBet × 100`; the purchase multiple affects the charged amount only and never changes the Redis multiplier. One member encodes all steps. The Controller claims once at paid start from the matching prefix and projects every later `type=2` from the same member. Empty Redis fails with an explicit 503 envelope.

Trusted complete-Round counts reused this continue-run: ordinary loss 1,137, ordinary win 194, purchase type=3/4/5 20 each, natural special 56. Natural scatter-feature remains `SAMPLE_INSUFFICIENT` versus a 30-round natural-special quota; the production `generation.special-count` entry stays disabled. Internal feature generation is tested, but the natural mode 1→2 third-Scatter transition is not accepted for production. Purchase quotas are MET from `captures/2300-Monster-Slayer/buy-modes/`.

Feature payouts include global ICE multiplier, upgraded ICE Wild local ×2, split-cell path multiplicity and reward bottom-row multiplier. Purchase-opening `tw` credits the wallet; `f.tw` starts at zero and only accumulates subsequent feature deliveries.
